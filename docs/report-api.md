# 유저·방 신고 API

모든 API는 프로필 등록을 완료한 회원의 액세스 토큰(`Authorization: Bearer ...`)이 필요합니다. 인증이 없거나 유효하지 않으면 `401`, 온보딩 토큰이면 `403`입니다.

## 화면 연결

- 사용자를 누르면 `GET /users/{userId}/profile`로 공개 프로필을 표시합니다. 응답 필드는 `id`, `nickname`, `avatarUrl`, `bio`, `favoriteKboTeam`, `favoriteKleagueTeam`, `blocked`입니다. 팀 형식은 기존 마이페이지와 같습니다. `blocked`는 조회자 본인이 차단했는지를 뜻하며 상대의 차단 여부는 노출하지 않습니다. 프로필이 없거나 활성 회원이 아니면 `404`입니다.
- 상대 프로필의 신고하기 → 유저 사유 조회 → 사유 하나 선택 → 필수 상세 내용 입력 → 유저 신고 제출 순서로 연결합니다. 본인 프로필에서는 신고하기를 표시하지 않습니다.
- 방 목록의 더보기 → 신고하기, 참여 중인 채팅방의 우측 상단 메뉴 → 신고하기는 같은 방 신고 API를 사용합니다. 메뉴에는 참여자 목록과 기존 나가기 기능도 표시합니다. 방에 참여하기 전에도 신고할 수 있습니다.
- 신고 화면을 열 때 서버의 `enabled`를 확인합니다. `false`라면 신고 버튼을 숨기거나 비활성화하고, 열린 화면에서 제출 시 `503`이 오면 접수 중단 상태로 안내합니다.

## 사유 조회

`GET /api/reports/reasons?targetType=USER` 또는 `targetType=ROOM`을 사용합니다. 종류는 대문자이며 필수입니다. 비활성화 상태에서도 목록과 `enabled=false`를 반환합니다.

```json
{
  "enabled": true,
  "targetType": "USER",
  "descriptionRequired": true,
  "descriptionMaxLength": 2000,
  "reasons": [
    {"code": "ABUSE", "label": "욕설·비방·혐오 표현"}
  ]
}
```

위 `reasons`는 형식 예시이며 실제 응답에는 해당 종류의 모든 사유가 표시 순서대로 포함됩니다. 화면에는 `label`을 표시하고 제출할 때는 `code`를 보냅니다.

| 코드 | 표시 문구 | 유저 | 방 |
| --- | --- | --- | --- |
| `ABUSE` | 욕설·비방·혐오 표현 | O | O |
| `HARASSMENT` | 괴롭힘·위협·스토킹 | O | |
| `SEXUAL_CONTENT` | 음란·성적 불쾌감 유발 | O | O |
| `SPAM` | 광고·도배 | O | O |
| `FRAUD` | 사기·금전 요구 | O | O |
| `PRIVACY_VIOLATION` | 개인정보 노출·침해 | O | O |
| `IMPERSONATION` | 타인 사칭 | O | |
| `INAPPROPRIATE_PROFILE` | 부적절한 닉네임·프로필 사진 | O | |
| `MISLEADING_ROOM_INFO` | 허위 경기·모집 정보 | | O |
| `ILLEGAL_ACTIVITY` | 불법 거래·활동 유도 | | O |
| `OTHER` | 기타 | O | O |

## 신고 제출

| 메서드 | 경로 | 상세 내용 |
| --- | --- | --- |
| `POST` | `/api/reports/users/{userId}` | 필수, 공백뿐인 내용 불가 |
| `POST` | `/api/reports/rooms/{roomId}` | 선택, 생략·null·빈 문자열 허용 |

```json
{
  "reason": "FRAUD",
  "description": "입장권을 보내겠다며 송금을 요구했습니다.",
  "clientReportId": "0f85ee57-bc8e-4558-831e-9dd9f642b1b6"
}
```

- `reason`은 해당 종류에 속한 사유 한 개입니다. 상세 내용은 최대 2000자이고 앞뒤 공백을 제거합니다. 방 신고의 빈 내용은 null로 저장합니다.
- `clientReportId`는 선택 사항인 UUID입니다. 앱은 제출할 때 새 UUID를 만들고 네트워크 재전송에는 같은 UUID를 사용하면 중복 접수를 막을 수 있습니다. 생략하면 각 요청을 새 신고로 접수합니다. 같은 신고자의 같은 UUID로 대상·사유·정규화된 내용이 같으면 기존 접수 결과를 `200`으로 반환합니다. 내용이나 대상이 다르면 `409`입니다. 다른 신고자의 UUID와는 독립적입니다.
- 본인 유저 신고와 본인이 최초 생성한 방의 신고는 `400`입니다. 존재하지 않는 대상과 활성 회원이 아닌 유저는 `404`입니다. 차단한 상대도 신고할 수 있고, 방 신고에 참여 여부·정원·경기 날짜 제한은 없습니다.
- 신고자는 토큰에서 결정합니다. 요청에 사용자 ID나 처리 상태를 추가해도 신고자나 접수 상태를 바꾸지 않습니다.

최초 접수는 `201 Created`입니다.

```json
{
  "id": 24,
  "targetType": "USER",
  "targetId": 7,
  "reason": "FRAUD",
  "status": "PENDING",
  "createdAt": "2026-11-06T12:00:00"
}
```

사유·내용·UUID 형식 오류는 `400`, 신고 접수 비활성화는 `503`입니다. 접수된 방이 삭제되어도 같은 UUID를 이용한 동일 요청의 재전송은 기존 결과를 반환합니다.

## 보관·설정·관리자 연동

- Flyway `V8__user_and_room_reports.sql`이 기존 `report` 테이블을 확장합니다. 기존 유저 신고는 사유·신고자·대상 ID·시각을 유지하고 `USER`, `PENDING`과 대상 프로필 정보를 채웁니다. 기존 사유 문자열도 그대로 보존합니다.
- 신고 당시 유저의 닉네임·사진 키·소개 또는 방의 제목·경기 날짜·경기장·팀·최초 생성자·현재 방장·정원을 JSON 스냅샷으로 보관합니다. 대상에 대한 외래 키를 두지 않아 방 삭제로 신고가 사라지거나 방 삭제가 막히지 않습니다.
- 신규 신고는 `PENDING`으로 저장합니다. 향후 관리자 처리를 위한 상태는 `PENDING`, `REVIEWING`, `RESOLVED`, `DISMISSED`입니다. 일반 사용자에게 신고 목록이나 상세 정보를 읽고 상태를 변경하는 API는 제공하지 않습니다.
- 관리자 페이지가 없어도 접수는 동작합니다. 외부 전송은 하지 않으며, 이후 관리자 인증을 갖춘 조회·처리 API와 웹 화면을 이 DB에 연결합니다. 신고 자체는 차단·정지·퇴장 동작을 수행하지 않습니다.
- `REPORTS_ENABLED=true`가 기본값입니다. `false`로 변경하고 서버를 재시작하면 제출을 차단하고 사유 조회에서 `enabled=false`를 반환합니다. Docker Compose도 같은 환경변수를 지원하며 변경 후 앱 컨테이너를 다시 생성해야 합니다. 기존 DB 기록은 보존합니다.
